# Контекст проекта
## Назначение и стек
- Telegram-бот на Python 3.11 + aiogram 3.31.0; зависимости зафиксированы в `requirements.txt` (`aiohttp-socks==0.12.0`). Запуск: `python main.py`; тесты: `pytest -q`.
- Бот сканирует одиночные IPv4 и заданные `/24`, ведёт историю, личные списки мониторинга, ежечасно проверяет IP, шлёт персональные отчёты/групповые алерты и имеет админ-панель.
- ICMP выполняется локальным `ping` subprocess напрямую, НЕ через прокси. `PROXY_URL` относится только к соединениям бота с Telegram.

## Архитектура
- `config_core.py` — чистое ядро без Bot/Dispatcher: env-парсер, пути/данные, `PingThrottle`, `ActiveUserRegistry`, ping, валидация/классификация целей, история, форматирование, callback-кодирование.
- `config.py` — runtime: загружает env, создаёт `Bot`, `Dispatcher`, сессию и глобальный throttle; реэкспортирует функции core для совместимости. Требует `TOKEN` уже при импорте. `set_proxy()` меняет сессию и возвращает старую — вызывающий код должен `await old.close()`.
- `main.py` регистрирует outer-middleware, подключает роутеры и запускает supervisor для фонового мониторинга.
- `handlers/`: `start.py` справка; `scan.py` интерактивное сканирование; `tree.py` история; `monitor.py` команды и hourly tick; `admin.py` настройки/рассылка; `middlewares.py` автозапись пользователя.
- `delivery.py` — retry для Telegram flood-control (`safe_send`, `safe_edit`) и pacing рассылок.

## Ключевые правила и поведение
- Цели проходят строгую `ipaddress.IPv4Address` проверку; `x.x.0` разворачивается в 256 адресов. Сеть `x.x.0.0` запрещена. Одиночные IP в истории имеют тип `host`, скан сети — `subnet`.
- Общий объект `config.throttle` ограничивает пинги; лимит меняется через `resize()` на лету. Интерактивно разрешена одна операция на пользователя через `active_users`, TTL 30 минут; hourly monitor этот реестр не использует.
- Данные лежат в `DATA_DIR` (по умолчанию `data/`): `networks_history.json` (cap 500), `tracked_ips.json`, `users.json`, результаты `results/result_<uid>.txt`. Старые JSON из корня мигрируют при `init_files()`.
- История/мониторинг хранятся в JSON-файлах, не в БД. Пользователь регистрируется при любом update через middleware.
- `/tree` режет вывод до 3500 символов; пользовательский текст экранируется для HTML. Кнопка удаления dead IP кодирует максимум 11 IPv4 в callback (<64 байт) и удаляет только из списка нажавшего.
- Telegram-доставка повторяется по `retry_after`; массовые отправки замедляются. Монитор обрабатывает пользователей параллельно, изолирует ошибки, hourly loop и supervisor восстанавливаются после сбоев.
- Админ-панель (`ADMIN_ID`) меняет лимит пингов/прокси, показывает статистику, чистит историю и запускает отменяемую рассылку.

## Проверки и инфраструктура
- Тесты в `tests/` покрывают валидацию, throttle/registry, ping (с subprocess mocks), monitor, историю/tree, env parser, delivery retries и cleanup callback. Для безопасного импорта `config` тестовый `conftest.py` подменяет `TOKEN`, `DATA_DIR`, `ENV_FILE`.
- Docker: `Dockerfile` ставит `iputils-ping`, зависимости из requirements и копирует код выборочно. `docker-compose.yml` использует `DATA_DIR=/app/data`, `ENV_FILE=/app/data/.env`, `env_file: .env`, тома `./data:/app/data` и `./data/.env:/app/data/.env:ro`.
- Секреты и runtime-файлы должны оставаться вне git/образа (`.gitignore`, `.dockerignore`). В репозитории присутствует локальный `.env`; его содержимое не включено в эту заметку и не следует выводить/коммитить. В `FIX_PLAN.md` указано, что ротация боевого токена и пароля прокси требует ручного подтверждения владельца; не считать её выполненной без отдельной проверки.

## Практические ориентиры для будущих изменений
- Начинать чистую логику с `config_core.py`; учитывайте, что `config.py` создаёт Telegram runtime уже при импорте.
- Сохранять публичные импорты из `config`, так как handlers и тесты их используют.
- Перед изменением данных/поведения смотреть соответствующий тест и `FIX_PLAN.md` (там есть история решений, но также устаревшие исходные пункты — сверять с текущим кодом).
- Некоторые функции форматирования/истории продублированы в core и handler-ах; перед правкой определить реально используемый путь.
- Последняя проверка в этой сессии: команда `pytest -q` не запустилась, потому что `pytest` не найден в PowerShell PATH; тесты не подтверждены.
